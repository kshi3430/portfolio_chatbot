## [JICHINI / 개발 내용] Jev 기반 입력 판단 및 LangGraph 응답 분기

TypeSafe Jev를 연동해 현재 입력과 이전 맥락을 바탕으로 사용자 의도, 매칭 요청 여부, 정보 충분성, 확인 질문 응답을 한 번의 요청으로 판단했습니다.
LangGraph로 상담 중심 흐름을 구성해 구체적인 고민이 확인되면 공감 답변과 함께 매칭 여부를 먼저 묻고, 사용자 확인(HITL)에 따라 유사 사용자 매칭, 상담 이어가기, 과거 고민 복귀, 결과 더보기로 분기했습니다.
고민 정보가 부족할 때는 바로 매칭하지 않고 상황이나 감정을 자연스럽게 물어볼 수 있도록 안내 답변 프롬프트를 설계했습니다.
- **기술**: TypeSafe Jev, LangGraph, LangChain, Python, HITL

## [JICHINI / 개발 내용] pgvector 기반 유사 사용자 매칭

고민 원문과 검색 데이터를 분리했습니다. PostgreSQL·pgvector에 실제 사용자 ID와 고민 원문을 내부 데이터로 보관하고, 추천 결과에는 무작위 추천용 ID, 지역, 공개용 주제 요약만 반환했습니다.
서버 내부에서 로컬 한국어 NER(KoELECTRA)과 정규식으로 이름·연락처·주소 등 식별정보를 가린 뒤 고민의 구체적인 상황을 Upstage Solar Embedding 1 Large로 벡터화했으며, 비식별에 실패하면 외부 API를 호출하지 않습니다.
캐시된 비식별 검색 문장으로 지역 필터 기반 코사인 유사도 검색을 실행하고, 비슷한 고민이 적을 때는 거리 기준에 따라 안내 문구를 함께 표시하며 '더 보여줘' 요청 시 첫 검색 순서를 유지하되 수정·삭제된 후보는 자동으로 제외합니다.
- **기술**: PostgreSQL, pgvector, Upstage Solar Embedding 1 Large, KoELECTRA, NER, RAG, Vector DB

## [JICHINI / 개발 내용] PostgreSQL 영속 대화 메모리

대화가 끊기지 않도록 나누던 대화, 현재 고민 요약, 확인 대기 상태를 모두 PostgreSQL에 저장해 서버가 재시작되거나 다시 접속해도 대화를 이어갈 수 있도록 구현했습니다.
같은 사용자가 메시지를 연속으로 빠르게 보내더라도 DB 잠금(Advisory Lock)으로 요청을 순서대로 처리해 상태가 꼬이지 않도록 했습니다.
최근 대화는 최대 5,000토큰(최소 2턴 보장) 한도 안에서 불러오고, 중간에 추천해 준 다른 사용자의 고민 목록은 AI가 사용자 본인의 고민으로 착각하지 않도록 짧은 시스템 기록('유사 사용자를 추천함') 한 줄로 분리해 전달했습니다.
오래된 대화가 잘려도 핵심을 잊지 않도록 관련 인물·사건·감정·상황·원하는 도움을 개인정보를 가린 상태로 누적 유지하며, 요약이 1,000토큰을 넘을 때만 600토큰 이하로 자동 압축하도록 설계했습니다.
또한 로그인한 사용자는 이전 고민을 최대 30개까지 장기 보관할 수 있으며, 과거 고민 복귀 요청 시 보관된 고민이 10개 이하이면 DB 목록에서 바로 찾고 10개를 넘으면 pgvector 유사도 검색으로 상위 5개 후보를 추린 뒤 찾아줍니다.
- **기술**: PostgreSQL, pgvector, Advisory Lock, Python

## [JICHINI / 개발 내용] AI 백엔드 API 구현

회원가입·정보 수정·탈퇴에 맞춰 PostgreSQL·pgvector의 고민 원문과 검색 벡터를 등록·갱신·삭제하는 API를 구현했습니다. 수정 시 추천용 ID를 새로 교체하고, 탈퇴 시 원문·벡터·대화 메모리를 하나의 트랜잭션에서 함께 파기합니다.
- **기술**: FastAPI, Python, PostgreSQL, pgvector

## [JICHINI / 문제와 해결] 모호한 고민 구체화와 판단 호출 줄이기

- **문제**: 사용자가 '요즘 그냥 좀 힘들어'라고 입력하면 LLM은 이를 고민으로 분류했지만 어떤 상황이 힘든지 알기 어려워 비슷한 고민을 가진 사용자를 추천하기에는 정보가 부족했습니다. 1차로 고민 구체성 점수를 도입해 기준 미달 시 구체화 유도 질문을 반환했으나, 입력 분류 뒤에 구체성 평가를 별도로 수행하면서 매칭 여부 결정까지 순차 호출이 발생해 비용과 응답 대기 시간이 늘어나는 한계가 있었습니다.
- **해결**: TypeSafe Jev를 도입해 현재 입력과 이전 고민을 바탕으로 입력 의도와 매칭 가능성을 한 번의 요청에서 함께 판단하도록 재구성했습니다. LangGraph는 그 결과를 받아 정보가 충분하면 PostgreSQL에서 유사 사용자를 검색하고, 부족하면 추가 질문을 생성하며, '더 보여줘'로 분류되면 세션에 저장된 추천 결과에서 다음 목록을 반환하도록 분기했습니다.
- **결과**: 별도 수행하던 두 판단을 Jev 호출 한 번으로 통합해 전체 응답 시간 p95가 3,212ms에서 1,784ms로 44.4% 감소했고, 도입 전후 각 70턴에서 측정한 Solar Pro 4·Upstage 임베딩·Jev의 토큰 사용량 기준 1,000턴 예상 API 비용이 28.9% 절감되었습니다.
- **기술**: TypeSafe Jev, LangGraph, LangChain, PostgreSQL, Python

## [JICHINI / 문제와 해결] 유사 사용자 검색 방식 개선

- **문제**: 일반적인 RAG처럼 벡터 검색에 키워드 검색(BM25·규칙 키워드)을 RRF로 결합하거나 로컬 Cross-Encoder로 결과를 재정렬하면 매칭 정확도가 더 높아질 것으로 예상했습니다. 하지만 일상 고민은 같은 상황을 서로 다른 구어체로 표현하는 경우가 많아('토요일 일요일' vs '주말', '남 욕' vs '험담'), 100명 후보·32건 평가셋으로 비교해 보니 단어가 정확히 겹치지 않는 정답을 키워드 점수가 오히려 뒤로 밀어내 정확도가 84.6%(22/26)까지 떨어졌습니다. 로컬 Cross-Encoder도 100개 쿼리 평가에서 벡터 단독(47/57)보다 낮은 39/57을 기록했고 CPU 추론 지연(p50 950ms)만 늘어났으며, 단순 하이브리드 검색만 쓰면 인사·잡담이나 정보 부족 요청에도 무조건 추천을 띄워 헛매칭이 발생했습니다.
- **해결**: 키워드 RRF와 리랭커를 기본 검색에서 제외하고, 개인정보만 가린 고민 상황 문장의 벡터 단독 검색에 TypeSafe Jev 의도·정보 충분성 판단을 결합하는 구조로 확정했습니다. 인사·잡담·정보가 부족한 입력은 검색 전에 차단하고, 구체적인 고민일 때만 벡터 검색을 실행하도록 구성했습니다.
- **결과**: 구어체·우회 표현이 많은 고민에서도 높은 매칭 정확도를 유지하면서 불필요한 지연과 헛매칭을 함께 없앴습니다. 격리된 PostgreSQL 17·pgvector 환경에서 합성 후보 100명·평가셋 32건에 실제 Jev·Upstage·로컬 NER·로컬 BGE 모델을 연결해 측정한 결과, 검색 정확도(Top-1)가 84.6%에서 96.2%로 11.6%p 향상되었습니다.
- **기술**: PostgreSQL, pgvector, TypeSafe Jev, Upstage Solar Embedding 1 Large, KoELECTRA, BGE, Python
